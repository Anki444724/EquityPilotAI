Everything needed to take this from a repository to a live HTTPS URL.

**Status: prepared and verified locally; not deployed.** This sandbox has no
Railway or GitHub credentials, so tasks 6–16 could not be executed here. What
follows is tested automation, not instructions written from memory — the
verification suite in §6 was run against a live instance in both development
and production auth postures.

## 2. Required environment variables

### Must be set — the app refuses to start without them

| Variable | Value | Why |
|---|---|---|
| `SECRET_KEY` | 48-byte urlsafe random | Signs every JWT. A predictable key lets anyone mint an admin session. Generated by the deploy script. |
| `ENCRYPTION_KEY` | 48-byte urlsafe random | Derives the AES-256-GCM key for stored tenant secrets. **Rotating it makes existing secrets undecryptable.** |
| `ENVIRONMENT` | `production` | Forces secure cookies, HSTS, JSON logs, and the migration guard. |
| `NATIVE_AUTH` | `true` | Without it every caller resolves to the development identity as Super Admin. |

Generate the two secrets with:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

### Injected by Railway — never set by hand

| Variable | Source |
|---|---|
| `DATABASE_URL` | Postgres plugin, by reference |
| `REDIS_URL` | Redis plugin, by reference |
| `PORT` | Railway runtime |

Setting these manually breaks credential rotation: Railway updates the
reference when a database password changes, and a hard-coded copy goes stale.

### AI providers

| Variable | Required | Notes |
|---|---|---|
| `GEMINI_API_KEY` | Recommended | Primary. From <https://aistudio.google.com/apikey>. |
| `OPENROUTER_API_KEY` | Recommended | Fallback when Gemini fails or is out of quota. |
| `AI_PREFERRED_PROVIDER` | No | Blank uses the declared order. |
| `AI_MOCK_MODE` | No (`true`) | Keeps the offline provider as a floor so the AI layer degrades rather than errors. |

With neither key set the platform still runs — the AI layer serves grounded,
fully-cited template output and says so.

### Recommended production values

```
DEBUG=false
LOG_FORMAT=json
LOG_LEVEL=INFO
RATE_LIMIT_BACKEND=redis
COOKIE_SECURE=true
COOKIE_SAMESITE=lax
CSRF_ENABLED=true
METRICS_ENABLED=true
CORS_ORIGINS=["https://<your-app>.up.railway.app"]
EMAIL_LINK_BASE=https://<your-app>.up.railway.app
OAUTH_REDIRECT_BASE=https://<your-app>.up.railway.app
```

On the **worker service only**:

```
WORKER_ENABLED=true
SCHEDULER_ENABLED=true
```

Exactly one process may run the scheduler. Two, and every recurring job fires
twice — two backups, two retention sweeps.

The full 70-variable reference with commentary is `backend/.env.example`.

## 3. Deploy

```bash
export RAILWAY_TOKEN=<from https://railway.app/account/tokens>
export GEMINI_API_KEY=<your key>          # optional
export OPENROUTER_API_KEY=<your key>      # optional

./deploy/railway-deploy.sh
```

The script is idempotent — safe to re-run after a partial failure. It:

1. verifies the CLI and token;
2. links or creates the project;
3. provisions Postgres and Redis;
4. generates `SECRET_KEY` and `ENCRYPTION_KEY` and sets every variable;
5. deploys;
6. runs `alembic upgrade head` **explicitly**, so a migration failure is
   visible at deploy time rather than as a crash loop;
7. polls `/health/ready` until the service is live;
8. runs the verification suite in §6.

Secrets are set on the service and never printed or written to disk. Read them
back with `railway variables`.

### Manual equivalent

```bash
railway init --name ierp
railway add --database postgres
railway add --database redis
railway variables --set ENVIRONMENT=production --set NATIVE_AUTH=true \
  --set SECRET_KEY="$(python3 -c 'import secrets;print(secrets.token_urlsafe(48))')" \
  --set ENCRYPTION_KEY="$(python3 -c 'import secrets;print(secrets.token_urlsafe(48))')" \
  --set GEMINI_API_KEY="$GEMINI_API_KEY" --skip-deploys
cd backend && railway up
railway domain                     # allocates <name>.up.railway.app
railway run alembic upgrade head
```

## 4. Service topology

Three services from one repository:

| Service | Root | Start command |
|---|---|---|
| **api** | `backend/` | `alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*'` |
| **worker** | `backend/` | `python -m app.worker` |
| **web** | `frontend/` | `node server.js` |

`--proxy-headers` is not optional. TLS terminates at Railway's edge; without
it every client IP is recorded as the proxy's, so the rate limiter throttles
the entire internet as one caller and every audit row shows the same address.

`NEXT_PUBLIC_API_URL` is inlined at **build** time. Pointing the frontend at a
different backend requires a rebuild, not a variable change.

## 5. Migrations

Alembic was added during this phase. Previously the schema came from
`Base.metadata.create_all`, which creates missing tables and does nothing to
existing ones — so it cannot add a column, and a deploy carrying a model
change would start cleanly against a stale database and fail on the first
query.

```bash
railway run alembic upgrade head      # apply
railway run alembic current           # show revision
railway run alembic history           # list
alembic revision --autogenerate -m "…"  # create (locally, then review)
```

The initial migration was verified to build all 54 tables and to match the
model metadata exactly — no missing tables, no extras.

Two safeguards:

* The start command uses `&&`, so a failed migration **aborts the start**. The
  earlier `|| true` swallowed failures and started the app anyway.
* In production the app compares declared tables against present ones at
  startup and refuses to serve if any are missing. Failing at boot is louder
  and cheaper than a container that passes its health check and 500s on the
  first real request.

**Always review an autogenerated migration.** Alembic emits `DROP TABLE` for
anything not registered on `Base.metadata`, so a model module that is not
imported in `alembic/env.py` will have its tables dropped.

## 6. Verification

```bash
python3 deploy/verify_deployment.py --url https://<app>.up.railway.app
```

34 checks across HTTPS, backend, security headers, data modules, AI, auth,
reports, portfolio and frontend. Exit code 0 only if every required check
passes; optional checks warn without failing, because a feature needing a paid
key should not block an otherwise sound deploy.

Run locally against both postures:

| Posture | Result |
|---|---|
| `NATIVE_AUTH=true` (production) | **27/31 passed**; the only required failure was `scheme is https`, correct for localhost |
| `NATIVE_AUTH=false` (development) | Passes except https and the two auth checks, which correctly detect the open dev identity |

The suite is auth-aware: a `401` from a protected route is a **pass**, because
it proves the module is mounted and guarded. A `404` (not registered) or `500`
(registered and broken) is a failure.

### Two bugs found in the verifier itself

Recorded because a verification tool that lies is worse than none:

1. **Case-sensitive header lookup.** `dict(response.headers)` discards HTTP's
   case-insensitivity — urllib returns lowercase keys, so
   `headers.get("X-Frame-Options")` was always `None`. The tool reported all
   five security headers as absent on a service sending every one of them.
   Fixed with a case-insensitive mapping.
2. **Stale variable reuse.** The security-header block read a `headers`
   variable last assigned by a different request. Fixed by re-reading.

## 7. AI provider behaviour in production

Fallback order is declared in `providers/router.FALLBACK_ORDER`:

```
Gemini → OpenRouter → OpenAI → Claude → Offline
```

The chain skips any provider without a key, so configuring one is enough and
configuring none is safe.

### Diagnosing "the AI isn't working"

```bash
curl https://<app>.up.railway.app/api/v1/ai/health
```

`/ai/providers` reports what is *configured*; `/ai/health` reports what
actually **answers**. The distinction matters: a key can be present, correctly
formatted and entirely out of quota, and only a live call tells them apart.

That is not hypothetical. The Gemini key used during this phase authenticates
correctly and returns 429 on every generation because its free-tier daily
allowance is spent:

```json
{
  "chain": ["Gemini", "Offline"],
  "providers": [
    {"provider": "Gemini",  "status": "quota_exhausted", "detail": "allowance spent"},
    {"provider": "Offline", "status": "ready"}
  ],
  "degraded": true,
  "serving": "Offline"
}
```

`degraded: true` is the signal to alert on — it means no live model is
reachable and the platform is serving template output.

### Quota versus throttling

A 429 means two different things and the router treats them differently:

| Condition | Behaviour |
|---|---|
| Throttled (too many requests this minute) | Retried up to 3 times with backoff — it clears |
| Quota exhausted (daily allowance spent) | Falls through to the next provider **immediately** |

Retrying a spent quota costs eight seconds of user latency to reach a
conclusion available at once. The distinction is read from the provider's own
error body, not guessed.

## 8. Security notes specific to this deployment

**The Gemini API key travels in the URL query string.** `httpx` logs every
request at INFO as `HTTP Request: POST <full url>`, which printed the
credential in clear text to stdout — and from there to Railway's log stream
and any aggregator collecting it. Observed directly during integration.

Module 10 redacts credentials from the application's own structured logs, but
this line comes from the transport library beneath that layer, so the
redaction never saw it. Fixed by raising the `httpx` and `httpcore` loggers to
WARNING. A test now captures every log record emitted during a provider call
and asserts the credential is absent.

Other guarantees, each enforced by test rather than promised:

* No API key appears in any source file (regex scan over four key formats).
* No provider module reads `os.environ` directly — configuration is one path.
* `/ai/providers` strips the query string before publishing an endpoint.
* `.gitignore` covers `.env`, `**/.env`, `*.pem`, `*.key`, `credentials.json`
  and `service-account*.json`.
* The key is absent from every commit in git history (verified).

## 9. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Crash loop, logs show missing tables | Migration did not run | `railway run alembic upgrade head` |
| `/health/ready` returns 503 | A critical check failed | Read `checks[]` — it names the problem |
| Every audit row shows the same IP | Missing `--proxy-headers` | Add it to the start command |
| Rate limit trips almost immediately | Same cause — all traffic looks like one caller | Same fix |
| AI always returns template text | No key, or quota spent | `curl /api/v1/ai/health` |
| 401 on every request after deploy | `NATIVE_AUTH=true` with no account yet | Register through the UI, then promote to `super_admin` |
| Frontend calls `localhost:8000` | `NEXT_PUBLIC_API_URL` is inlined at build | Rebuild with the right value |
| Recurring jobs run twice | Two processes with `SCHEDULER_ENABLED=true` | Enable on the worker only |
| Every ₹ is a black box in a PDF | DejaVu fonts absent | Already in the Dockerfile |

## 10. Post-deploy checklist

```bash
# 1. Live and ready
curl -fsS https://<app>.up.railway.app/health/ready | jq '.ready'

# 2. No failing readiness checks
curl -fsS https://<app>.up.railway.app/health/ready \
  | jq '.checks[] | select(.ok==false)'      # must be empty

# 3. Full verification
python3 deploy/verify_deployment.py --url https://<app>.up.railway.app

# 4. AI providers
curl -fsS https://<app>.up.railway.app/api/v1/ai/health | jq '.serving, .degraded'

# 5. Load real company data (optional; ~8 minutes for 135 companies)
railway run python -m app.data

# 6. Prove a backup restores — not that one exists, that one restores
curl -X POST https://<app>.up.railway.app/api/v1/platform/backups
```
